# Architecture and trust boundaries

```text
Browser (authenticated same-origin HTTPS or localhost)
  └─ Go Manager web process (dedicated non-root account)
      ├─ Embedded Vite/React assets, Monaco workers, CSS, icons
      ├─ Session authentication, origin/CSRF checks, REST API
      ├─ Shared read-only gRPC subscriber → loopback sing-box native API
      └─ Restricted Unix socket → Manager deployment helper (root)
          ├─ Effective systemd discovery → fixed unit and source paths
          ├─ Raw JSON + content hashes → drafts and version history
          ├─ Installed sing-box schema/check → validation
          ├─ Persistent transaction → atomic replacement → restart/health
          ├─ Recovery before accepting requests after a crash
          └─ journalctl fixed unit → redacted bounded browser log stream
```

## Processes and authority

The web service explicitly refuses root execution. Production uses the `sing-box-manager` account with an empty capability bounding set, protected system/home files, and a private writable state directory. The helper socket is root-owned, group-restricted, and only accessible to the Manager group. Helper executable arguments define the unit and source paths; HTTP callers cannot supply shell commands, arbitrary file paths or arbitrary unit names. No shell is used for backend subprocesses.

The helper must access existing sing-box configurations and systemd. Its private state contains raw secrets in drafts/backups, with owner-only permissions. A web administrator is a trusted sing-box administrator and can intentionally change its routes, credentials and file references. This is not a tenant isolation system. Do not grant access to untrusted users.

## Native configuration model

Frontend forms update object properties in the same configuration object used by Monaco. They do not reconstruct entire documents from a fixed catalog. Protocol schemas are generated by the installed executable and resolved from its `$defs`, union alternatives and discriminators. Unknown properties remain unless an administrator explicitly edits or deletes them. The installed checker remains authoritative for cross-field/protocol requirements.

Single-source JSON supports write-back. Multi-source configurations are discovered and inspected using the installed merge semantics, while retaining source paths and read-only status. This is deliberate: silently moving all configuration into one file would change ownership, ordering and external management workflows. JSONC sources also get a normalized read-only inspection view while preserving their original bytes. Directory sources are refreshed, and changes to the effective service command identity block old deployments until rediscovery.

Drafts retain the hash of the live file at creation. Save and apply reject outdated hashes. Apply checks the hash again after validation. External editors do not share Manager's lock, so an operating-system filesystem cannot provide a universal compare-and-swap against arbitrary external writers; administrators should avoid simultaneous edits during an apply. The UI polls changes and blocks known conflicts.

## Deployment transaction

The helper serializes its operations. It validates the candidate with the installed binary, writes a restricted timestamped backup, persists a deployment transaction, atomically replaces the file, restarts the managed unit, and verifies service/listener/native API health. It commits only after checks pass. Failure restores the backup and verifies recovery. A failed recovery keeps the transaction and blocks subsequent apply attempts.

The web process never owns the transaction lifecycle. A dropped browser request or crashed web process does not cancel a deployment. If the helper crashes or the machine reboots mid-transaction, its systemd service restarts and rolls back before serving new requests. Backup history restoration always creates a draft; there is no direct restore-without-validation endpoint.

Health checks verify process and supported local listeners/API. They do not prove that every remote outbound, DNS resolver, TLS certificate, ISP path or client credential works. Operators should run controlled end-to-end checks for their deployment; the included real binary integration test demonstrates a disposable HTTP proxy path.

## Telemetry and streaming

One shared native gRPC subscription supplies all browser SSE clients. It samples at one-second intervals, uses actual totals, drops stale rates, reconnects and bounds retained connection details. Browser chart history is bounded to fifteen minutes. Journald streams are limited to the configured unit and the browser retains a bounded buffer. Pause affects the displayed stream, not system journal storage. Neither production path imports mock data.

## Packaging

The Vite build is copied into `backend/internal/web/dist` and compiled with Go `embed`. The release bundles one Manager binary plus reviewed installation scripts and units. Target architectures are Linux amd64 and arm64. The production runtime requires neither Node nor Docker. Docker is used only for isolated Linux/systemd installer verification.

## Security controls

- Loopback listener and actual socket binding, persisted port and per-state-directory lock.
- Cryptographically random token in a restricted file; random, expiring, HttpOnly/SameSite browser sessions.
- Same-origin checks, no permissive CORS, cross-site request rejection, bounded request bodies, login throttling, CSP and no-referrer policy.
- No token in URL or public frontend assets. Raw configuration is available only to logged-in administrators.
- Fixed helper routes and fixed subprocess executables/arguments; no arbitrary shell endpoint.
- Native telemetry targets literal loopback addresses; TLS verification is never disabled.
- Version-pinned download verification and archive extraction path/link checks.
- Tailscale configuration preserved on conflict; Funnel is never invoked.

See `docs/verification.md` for verification scope and unresolved compatibility limitations.
